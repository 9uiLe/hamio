# hamio 基本設計

hamio は、開発用スクリプトの入力フォーム、進捗、表、結果を統一するターミナル UI ツールである。利用側の実装言語や業務処理に依存せず、CLI と JSON を通じて対話と表示を引き受ける。人には端末上の操作画面を、AI エージェントと CI には非対話で扱える構造化データを提供する。

本書は製品の責務、公開契約、品質条件、開発・配布方針の正本である。実装状況は [README](../README.md)、作業コマンドは[開発手順](development.md)、判断根拠は[技術資料](#根拠資料)に記載する。詳細仕様として確定が必要な項目は[第13節](#13-詳細仕様の確定項目)に列挙する。

## 1. 目的と対象範囲

プロジェクトごとに異なるスクリプトでも、質問、確認、状態、結果を同じ規則で読み取れるようにする。UI の実装と保守を共通化し、利用者の操作理解と開発者の実装にかかる負担を抑える。

| 項目     | 設計方針                                                                       |
| -------- | ------------------------------------------------------------------------------ |
| 利用言語 | Shell、Python、Go、TypeScript などからプロセス I/O と JSON で接続する          |
| 本体     | Bun + TypeScript で実装する                                                    |
| 配布     | 本体・UI 依存・Bun ランタイムを含む実行ファイルを macOS / Linux 向けに提供する |
| 利用条件 | hamio の UI を使うための Bun・Nix 導入を要求しない                             |
| 入力     | 文字入力、確認、単一選択、複数選択、秘密入力を扱う                             |
| 出力     | メッセージ、値の一覧、表、進捗、結果、エラーを扱う                             |
| 機械利用 | 事前入力と構造化出力を使い、対話待ちや不要な装飾を避ける                       |
| 品質     | 安全性、起動、応答、メモリ、CPU、出力量、業務への追加負荷を評価する            |

初期リリースはローカルのターミナル UI を対象とする。Web UI、常駐サービス、ネットワーク API、任意コードを実行するプラグイン、汎用ワークフロー言語、自由なテーマ、全画面ダッシュボード、自己更新は対象外とする。

製品の対応 CPU、最低 OS、Linux libc は配布物の実機検証に基づいて確定する。開発用 Nix shell の対応環境は、製品の動作保証範囲とは別に管理する。

## 2. 用語と責務

| 用語       | 定義                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 利用側     | hamio を呼び出すスクリプトと、それを管理するプロジェクト               |
| 業務処理   | API 呼び出し、ビルド、Git 操作、ファイル変更など、スクリプト本来の処理 |
| 入力定義   | 質問の項目、型、制約、ラベル、選択肢を表すデータ                       |
| 公開契約   | 利用側と hamio が共有する入出力データと動作規則                        |
| run        | 利用側スクリプトによる一回の業務実行                                   |
| task       | run 内で開始・進捗・完了・失敗を識別する処理単位                       |
| event      | task の状態変化などを通知する一件のデータ                              |
| 連続表示   | 一つの表示プロセスが event を受け取り、進捗と結果を更新する利用方法    |
| 描画       | 入力や状態のモデルを、表示文字と端末制御命令へ変換する処理             |
| 機械モード | 対話待ちと端末装飾を使わず、構造化データを返す動作                     |
| プレビュー | 開発中の端末出力から作る、レビュー用の画像と録画                       |

利用側は業務の実行、順序、並列数、権限、再試行、取り消しを管理する。Python、Git、利用側の TypeScript 実行環境など、業務に必要な環境も利用側が用意する。同梱する Bun は hamio 自身の実行に使用する。

| 利用側の責務                               | hamio の責務                                     |
| ------------------------------------------ | ------------------------------------------------ |
| 質問の内容、選択肢、値を定める             | 入力部品と共通の表示規則を提供する               |
| API 照会などを伴う業務上の妥当性を判断する | 型、必須条件、範囲などの基本入力検証を行う       |
| 業務を実行し、task の状態を通知する        | 通知を受信し、表示状態へ反映する                 |
| 秘密値を供給し、秘密項目を指定する         | 指定された秘密値の表示・ログへの漏えいを抑制する |
| 回答を業務へ適用する                       | 回答完了、不足入力、検証失敗、キャンセルを返す   |
| スクリプト全体の成否を判断する             | UI 自体の成功、失敗、中断を通知する              |

## 3. 実行構成

利用側は hamio を独立プロセスとして起動する。明示した入出力経路で JSON を交換し、実装言語の違いをプロセス境界で吸収する。公開契約は UI ライブラリから独立させ、ライブラリ固有の関数や設定を利用側へ公開しない。

```mermaid
flowchart LR
    U["利用側スクリプト"] --> B["業務処理<br/>API・Git・ファイル・並列実行"]
    U -->|入力定義・event・結果| C["hamio<br/>CLI・JSON の受け付け"]
    C --> M["入力検証・状態管理"]
    M --> H["人向け UI<br/>フォーム・表・進捗"]
    H -->|回答・キャンセル| M
    M --> R["構造化出力<br/>回答・結果・エラー"]
    R --> U
```

内部は、公開契約の受け付け、入力検証と状態管理、人向け描画、構造化出力に責務を分ける。一つの実行ファイル内で構成し、モジュール分割のための別サービスや常駐プロセスは設けない。

フォームと段階表示の UI 基盤は Clack を第一候補とする。採用条件は、日本語表示、端末復旧、Bun 同梱時の動作、性能予算を満たすことである。表や共通出力の依存も、機能、保守、配布コストを評価して選定する。

## 4. 利用方法とライフサイクル

### フォーム

利用側は関連する質問を一つの入力定義として渡す。hamio はフォーム単位で入力を扱い、回答完了、キャンセル、不足入力、検証失敗を区別して返す。プロセスの起動単位はフォームとする。

業務上の判断を伴う再質問は利用側が制御する。たとえば、接続先の選択後に利用側が接続可否を確認し、不成立なら理由を添えて新しい入力定義を渡す。入力定義には任意関数や実行コマンドを含めない。

### 単発表示

利用側はメッセージ、表、結果の内容と意味を渡す。hamio は指定された形式で表示して終了する。成功、警告、秘密といった区分は公開契約で指定する。

### 連続表示

利用側は一回の run に属する通知を一つの送信経路へ集約する。表示期間中は同じ hamio プロセスを使い、task や event ごとに UI プロセスを起動しない。

task の状態には開始、進捗、完了、失敗を持たせる。EOF は入力経路の終了を意味し、業務成功は明示的な通知で表す。利用側は業務結果と UI の終了状態を受け取り、スクリプト全体の終了コードを決める。

### 端末の共有と中断

一つの端末を描画する主体と、同時に有効な質問は、それぞれ一つとする。連続表示中にフォームが必要な場合は、利用側が公開契約に従って端末の使用を切り替える。切り替え時の停止・再開・終了の規則は詳細仕様で固定する。

回答を必要としない業務処理は並行して進められる構成とする。キャンセル時は入力モードと表示状態を復旧し、キャンセルを返す。業務を停止・継続・再実行する判断は利用側が行う。

## 5. 公開契約

入出力は [RFC 8259](https://datatracker.ietf.org/doc/html/rfc8259) に基づく JSON とする。契約には質問、回答、状態、結果の意味を定義し、関数、クラス、Bun 固有オブジェクトを含めない。

| データ     | 含める情報                                                    |
| ---------- | ------------------------------------------------------------- |
| 入力定義   | 契約版、項目 ID、入力型、必須条件、制約、ラベル、説明、選択肢 |
| 回答       | 項目 ID と値、回答完了・キャンセル・不足・検証失敗の状態      |
| 表示 event | task ID、順序を識別する情報、種別、状態、表示データ           |
| 業務結果   | 成否、結果データ、警告、省略の有無                            |
| UI エラー  | 安定したエラーコード、対象項目、説明、返却結果の有無          |

入力部品は text、confirm、select、multiselect、secret、出力部品は message、key-value、table、progress、result、error を対象とする。これらは部品の意味を表す名称であり、コマンド名や JSON フィールドの綴りは詳細仕様で固定する。

項目 ID と選択肢の値は表示ラベルから独立させる。入力制約は、表示順や説明と区別する。JSON Schema を採用する場合は対応制約を列挙し、未対応の制約を拒否する。外部参照をネットワークから自動取得しない。

実行ファイルと公開契約は別々に版を管理する。未知の major 版は UI 操作前に拒否する。任意項目の追加と必須動作の変更には、それぞれ互換性の規則を設ける。機能照会では必要な情報の範囲を選択できるようにする。

入力不正、UI 障害、キャンセル、業務失敗を別の状態として扱う。古い進捗、重複、順序違反、中断後の event の規則を定め、異なる run の状態を混在させない。大きな整数、日時、バイト列は利用言語間で同じ値を表せる形式を定義する。

## 6. 対話と出力の規則

人向け UI と機械向け出力は、共通の入力・状態・結果モデルから生成する。出力形式、対話の可否、色・端末制御の可否を独立した設定とし、明示指定を優先する。TTY の情報はストリームの接続先の判定に使い、人と AI エージェントの識別には使わない。

| 項目   | 人向け UI                      | 機械モード                                  |
| ------ | ------------------------------ | ------------------------------------------- |
| 入力   | 端末のフォームで受け付ける     | 事前指定値を検証し、不足項目を返す          |
| 進捗   | 更新を集約して描画する         | 既定は最終結果。要求時に必要な event を返す |
| 結果   | 表や説明で示す                 | 安定したキーの JSON を返す                  |
| エラー | 原因と対処を示す               | コード、対象項目、説明、結果状態を返す      |
| 装飾   | 端末能力と設定に従う           | ANSI 制御、spinner、カーソル操作を使わない  |
| 中断   | 端末を復旧してキャンセルを返す | キャンセルを結果状態と終了コードで返す      |

端末 UI は stderr、フォーム回答と機械向け結果は stdout を基本経路とする。回答用の stdout は利用側が捕捉する。機械モードでは stderr も管理し、描画や不要な診断の混入を防ぐ。

フォーム定義とキー入力は別の経路で受け付ける。定義ファイルを明示し、stdin でキーを受け、stdout に回答を返す構成などを詳細仕様で定める。連続表示は stdin を event の入力に使う。非対話モードで入力が足りなければ不足を返し、`/dev/tty` を開いて回答を待たない。

機械向け出力は、重複進捗、不要な説明、全スキーマの反復を抑える。大量データでは項目と範囲を選択可能にし、省略件数と続きの取得方法を示す。重要な警告、失敗、不足入力、機械向けの値を黙って切り捨てない。

token 消費は stdout・stderr の合計を対象に、エージェントの取得方法と tokenizer を指定して測定する。

## 7. 性能設計

hamio は利用側のビルドやテストと CPU・メモリを共有する。UI 本体に加え、利用側の JSON 生成、転送、待機、補助プロセスも性能評価に含める。

### 並列処理

業務の並列数と依存関係は利用側が制御する。複数 task の通知は一つの送信経路へ集約し、複数の送信元が同じ pipe へ直接 JSON を書き込む構成を避ける。業務の更新ごとに描画完了を待たせない。

I/O は非同期に待ち、同時受付数と待ち行列に上限を設ける。CPU 処理は入力規模、アルゴリズム、処理単位で評価する。Worker は生成・転送・状態保持・終了を含めて効果を確認できる場合に採用し、既定で全 CPU コアを占有しない。

I/O の非同期化と CPU の並列実行は別に評価する。UI 単体の応答と、業務処理を同時実行した場合の業務所要時間を測定する。

### 保持量と描画頻度

受信フレーム、文字列、階層、待ち行列の件数・バイト数、活動中 task、ログ、表に個別の上限を設ける。連続入力は上限付きのフレームとして処理する。

進捗は task ごとの最新状態に集約する。完了 task の詳細は用途に応じて解放し、ログと表は表示範囲を限定する。全件の集計、並べ替え、続きの取得は利用側が管理する。

進捗の描画頻度に上限を設け、状態が変わらない再計算を抑える。入力応答、エラー、完了は進捗の描画周期と独立して扱う。機械モードでは描画とアニメーション用 timer を起動しない。

### 混雑時の扱い

受信と描画を分け、出力先が遅い場合はデータの重要性に従って集約、待機、エラー返却を行う。有限メモリで受け付けられる量を契約に含める。

| データ               | 混雑時の規則                                                         |
| -------------------- | -------------------------------------------------------------------- |
| 途中の進捗           | 最新状態へ置換する。利用側でも可能な範囲で JSON 化前に集約する       |
| 詳細ログ             | 最近の一定量を保持し、省略件数を通知する。全件保存は利用側が管理する |
| 完了・失敗・重要警告 | 受付・配送の失敗を識別し、待機上限を超えたら明示的なエラーを返す     |
| 入力要求・回答       | 取得・返却の失敗を成功や肯定へ置き換えない                           |

UI 障害時の業務継続は利用側が判断する。待ち行列の上限と待機時間は代表データを用いて詳細仕様として固定する。

### 暫定性能予算

以下は初期リリースの設計目標である。基準機、OS、端末、Bun 版、入力データを定め、配布用実行ファイルで達成状況を判定する。

| 指標                   | 目標                                   | 測定条件                                                                                          |
| ---------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 小さい機械向け呼び出し | 起動から結果取得まで p95 100 ms以内    | 入出力各4 KiB以下。OS cache が温まった状態で新規起動し、cold start は別記する                     |
| 入力応答               | キー入力から表示反映まで p95 50 ms以内 | 日本語を含む通常フォーム。業務処理と人の思考時間を除く                                            |
| メモリ                 | 定常 RSS 64 MiB、peak RSS 128 MiB以内  | 1 run、100 task以内、最近のログ2,000行以内・各行1 KiB以内。補助プロセスを含む同時使用量も評価する |
| 業務への追加時間       | hamio なしの対照に対して5%以内         | 対照は5秒以上。同じ業務結果・並列数、人の入力待ちなし。短い処理は絶対追加時間も評価する           |
| 待機中の CPU           | 1 core換算で平均1%以下                 | 新着 event・アニメーションのない30秒区間                                                          |

p95 は応答の95%が収まる時間を指す。中央値、p95、試行数、ばらつきを記録し、外部 API の変動と人の操作時間を分けて扱う。

JS heap とプロセス全体のメモリを別に観測する。RSS、共有ページを按分する PSS、macOS の phys_footprint には、API・単位・OS を明記する。Worker のメモリを二重加算しない。複数プロセスの RSS 合計は、専有物理メモリとは異なる。

アプリ内の保持量上限と OS の厳密なメモリ制限を区別する。省メモリ設定、bytecode、Worker は一条件ずつ比較し、起動、応答、メモリ、CPU の改善と悪化を記録する。予算の変更には利用シナリオと測定根拠を必要とする。

## 8. セキュリティ設計

保護対象は開発マシン、利用側コード、認証情報、入力値、端末、配布物とする。入力定義、表示文字列、ログ、ファイル名、依存コード、ビルド資産を検証する。外部由来のデータは、所有者のスクリプトが取得したものも未信頼入力として扱う。

### 入力と秘密情報

入力の型、サイズ、深さ、件数を検証する。外部文字列に含まれる端末制御命令を無害化し、描画には hamio が生成した命令を使う。色用の SGR を含め、端末が解釈する命令を対象とする。

機械出力は JSON としてエスケープする。表示用の省略や無害化によって返却値を黙って変更しない。UI 定義から Shell、JavaScript、外部プラグインを実行する経路は設けない。

秘密項目は利用側が指定する。回答は呼び出し元が捕捉する経路で返し、表示、復唱、エラー、ログ、永続化への混入を防ぐ。自由文中の秘密の完全な自動検出は保証しない。

回答の返却経路には秘密の実値が存在する。受信後の保管、ログ、エージェントへの転送は利用側が管理する。表示マスク、暗号化、権限分離はそれぞれ独立した保護として設計する。

### 実行環境

通常の UI 利用はオフラインで完結させる。必要なコードを配布物に含め、Bun の暗黙の `.env`・`bunfig.toml` 読み込みをビルド設定で無効化する。実行時に依存を自動取得しないことを検証する。

起動前に作用する `BUN_OPTIONS` や `BUN_BE_BUN` は固定した Bun 版で確認する。起動環境の影響は、アプリ開始前の処理も含めて評価する。

hamio は利用者と同じ OS 権限で動作する。独立プロセスとランタイム同梱に sandbox の役割を持たせない。業務の権限、削除やデプロイの許可、子孫プロセスの停止は利用側が管理する。

## 9. 開発環境と品質検査

開発ツールは `flake.nix` と `flake.lock`、JS 依存は `package.json` と `bun.lock` で固定する。Bun は TypeScript とテストを、Node.js は開発用ツールを実行する。開発用の依存は利用者向け配布物から分離する。

開発用 Nix shell は `aarch64-darwin`、`aarch64-linux`、`x86_64-linux` を対象とする。ローカルと CI で同じ定義と lockfile を使う。依存取得と hooks 導入は明示的なセットアップで行い、通常の依存取得では lockfile の更新と lifecycle scripts の実行を禁止する。

| 工程      | 検査と確認                                                                    |
| --------- | ----------------------------------------------------------------------------- |
| 編集      | 保存時の format、型診断、対象のテストを利用する                               |
| UI 確認   | 最新のプレビューを用意し、画像と必要な録画を確認する                          |
| commit 前 | ステージ済みファイルを検査する。同時タスクは2に制限し、部分ステージを保持する |
| push 前   | 作業ツリー全体の Lint、format、型、テスト、プレビューの更新漏れを検査する     |
| PR        | Linux の1ジョブで全体検査、Nix 定義評価、検査前後の差分確認を行う             |

format は TS・JS・JSON を Biome、Markdown・YAML を Prettier、Nix を nixfmt、Shell を shfmt に統一する。ShellCheck と actionlint で Shell と workflow を検査する。TypeScript は strict 設定とし、宣言ファイルも型検査する。

検査コマンドと hooks はソースを自動修正しない。修正は明示的なコマンドで行い、差分を確認する。ローカルの pre-push は未コミットの内容も含む作業ツリーを検査し、PR の CI は GitHub 上のマージ候補を検査する。

自動 CI は `master` 向け PR の作成・更新・再開を対象とする。push と PR close は自動トリガーに含めない。Bun・Nix・hooks・OS に関わる依存を変更する場合は、macOS でも同じ検査を手動実行する。製品の端末 I/O、プロセス管理、配布物には両 OS の実行試験を設計する。

AI エージェントの入口は `AGENTS.md` とし、`.agents/skills` に設計、TypeScript、性能の判断基準を置く。作業に必要な領域だけを読み、機械的な検査と併用する。

## 10. 端末 UI のプレビュー

プレビューは実際の疑似端末出力から代表状態の PNG と操作の GIF を作り、PR とチャットでレビューする開発機能である。製品の表示確認では製品の入口を実行する。録画基盤の検証用プログラム `fixture` は、その用途を画像と文書に明記する。

### 確認の流れ

生成コマンドは、生成元と生成物の SHA-256 を照合する。内容が一致する生成物は再利用し、未生成・変更・破損がある場合は端末を実行して生成する。端末を必ず実行する操作には強制生成を指定する。

通常の hooks と CI は、版管理された PNG と生成元の照合だけを行う。検査は読み取り専用とし、画像生成と目視確認は開発者が明示的に行う。照合結果には変更対象と対処を示す。

| 生成物              | 保存と検証                                                           |
| ------------------- | -------------------------------------------------------------------- |
| 代表状態の PNG      | ソースと一緒に版管理する。生成元・画像の hash と生成環境を記録する   |
| GIF・端末出力の記録 | ローカルに保存する。専用の記録で生成元と各ファイルの hash を検証する |
| PR・チャットの画像  | 目視確認した PNG を掲載する。PR のリンクは対象 commit SHA に固定する |

画像の hash は更新漏れの検出に使う。表示の正しさは目視で確認し、各 OS の実端末、アクセシビリティ、製品性能は専用の試験で評価する。

### 記録と描画

シナリオは実行コマンド、端末サイズ、待つ出力、送るキー、撮影位置を定義する。Bun の PTY で出力を記録し、agg が ANSI とカーソル操作を解釈して描画する。静止フレームは Pillow で PNG に変換する。

端末出力はシナリオごとに一度保持し、代表画像の撮影位置を event 番号で指定する。PNG では期待する出力へ到達したら入力を送り、GIF では閲覧用の操作間隔を設ける。シナリオ内の処理と出力待機は、どちらの形式でも実行する。

録画と描画は順次実行し、CPU・メモリの同時使用を抑える。PNG の変換は一つの Pillow プロセスで行う。描画ツールとフォントは専用の Nix shell に固定し、反復作業では同じ shell を使用できる構成とする。

### 安全性と開発性能

シナリオにはダミーデータを使用し、子プロセスへ渡す環境変数を限定する。時間、出力量、event 件数、生成物サイズに上限を設け、入力不正、異常終了、不足画面、timeout を検出する。生成の前後に入力源を照合し、処理中に入力源が変わった場合は生成物を採用しない。

生成物は公開資料として内容を確認する。外部サービスへ自動送信せず、チャットには録画の出力全文を転記しない。

開発性能は、内容照合、再利用、再生成、Nix 起動を分けて測定する。経過時間、CPU、メモリ、試行数、測定条件を記録し、検査の保証と資源消費を合わせて評価する。[プレビューの性能評価](research/preview-performance.md)に測定結果を示す。

## 11. リポジトリ・配布・保守

### 公開リポジトリ

`9uiLe/hamio` は公開リポジトリとして運用し、変更権限を所有者に限定する。第三者の一般投稿を受け付けない運用とし、GitHub の投稿・レビュー制限を適用する。期限付き制限は失効前に確認する。閲覧、clone、fork は許容する。

CI は所有者の操作を対象とし、PR は同一リポジトリからのものだけを検査する。`pull_request_target` は使わない。トークンは読み取り権限に限定し、checkout 後に認証情報を保持しない。第三者のコードを無条件に実行したり配布物へ含めたりしない。

マージの必須条件は GitHub の branch ruleset で設定する。ローカル hooks、workflow の起動条件、GitHub 上のマージ制限は、それぞれ別に管理する。

### 配布と検証

製品は OS・CPU 別の実行ファイルとして GitHub Releases で配布する。版、対応環境、checksum、ビルドの由来を示す provenance、部品とライセンスの一覧である SBOM を添付する。公開後のタグと資産は immutable releases で固定する。

| 対象         | 固定・追跡する情報                                         |
| ------------ | ---------------------------------------------------------- |
| ツールと依存 | Nix 入力、Bun 版、JS 依存の lockfile                       |
| CI           | Actions と再利用 workflow の完全な commit SHA              |
| 生成物       | ソース commit、ビルド設定、バイナリ hash                   |
| 配布元       | `9uiLe/hamio`、公開 workflow、ソース ref / commit          |
| SBOM         | JS 依存、同梱 Bun/runtime、native 部品、取得元、ライセンス |

配布候補は Bun・Nix のない環境で実行し、通常の UI 利用に `/nix/store` とネットワーク取得が不要であることを検証する。開発環境の固定、配布ビルドの隔離、バイト単位の再現性は別々に確認する。配布ビルドを Nix derivation で定義するかは詳細仕様で確定する。

checksum は完全性の確認、provenance は配布元とビルド工程の確認に使う。検証ツールの取得経路も定める。SBOM は出荷物と照合し、同梱ランタイムや native 部品の記載漏れを確認する。依存固定、脆弱性検査、SBOM、provenance を組み合わせて評価する。

### 更新と脆弱性対応

ビルド権限と公開権限を分離し、公開権限は必要な工程に限定する。依存の取得元と差分を確認し、通常更新と緊急セキュリティ更新の手順を定める。同梱 Bun の脆弱性には hamio の再配布で対応する。

利用者は版を選択して明示的に更新する。検証に失敗した配布物は実行・置換しない。保守には影響版の告知、修正版の公開、非公開の脆弱性報告窓口を含める。

## 12. リリースの受け入れ条件

製品のリリース判定には配布用実行ファイルを使う。開発時の TS 実行、ツール取得、プレビュー生成は、製品性能とは別の測定対象とする。

| 対象         | 受け入れ条件                                                                            |
| ------------ | --------------------------------------------------------------------------------------- |
| 開発基盤     | 固定したツールと lockfile でローカル・CI の検査を再現できる                             |
| プレビュー   | 実行対象とシナリオを識別でき、生成元と画像が一致し、代表状態を目視確認できる            |
| 配布物       | Bun・Nix なしで動作し、通常の UI 利用に依存取得と `/nix/store` が不要である             |
| 多言語       | Shell・Python の回答・結果・エラーが一致し、Go・TS も標準プロセス I/O で接続できる      |
| 端末         | 日本語幅、emoji、狭い幅、resize、色なし表示、Ctrl-C、EOF、入力モードの復旧が機能する    |
| 機械モード   | 対話待ちと端末制御がなく、人向け UI と同じ値・業務状態を返す                            |
| 出力量       | 成功・失敗・不足入力・大量出力の byte と token を測定し、重要情報を保持する             |
| 性能         | 基準環境で暫定性能予算を評価し、利用側の JSON 生成・転送を含む追加負荷を記録する        |
| 並列・長時間 | 業務並列数と同時 run 数を変え、業務への影響、完了 task の累積、保持量を確認する         |
| 混雑・中断   | 大量 event、遅い端末・pipe、閉じた出力先で無期限待機や重要通知の黙った喪失がない        |
| 入力保護     | 巨大・不正 JSON、深い構造、制御文字、秘密を含むエラーを安全に扱う                       |
| 配布検証     | 改ざん、別 repository/workflow、想定外 commit の資産を拒否し、SBOM を出荷物と照合できる |

測定記録にはソース commit、Nix 入力、Bun 版、ビルド設定、hash、CPU、RAM、OS、端末、負荷状態、測定 API、単位、試行数を含める。通常測定と profile・強制 GC を伴う診断を分ける。

代表データと結果を回帰検知に用いる。Bun、UI 依存、配布方式の変更時には再検証する。hamio なし・ありで同じ業務を実行し、UI 単体と業務全体の両方を評価する。
