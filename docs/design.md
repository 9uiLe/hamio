# hamio 基本設計

hamio は、開発用スクリプトの入力フォーム、進捗、表、結果を共通化するターミナル UI ツールである。スクリプトの実装言語と業務処理を利用側に残し、CLI と JSON を境界として対話と表示を引き受ける。人には操作しやすい画面を、AI エージェントと CI には非対話で扱える構造化データを提供する。

本書は製品と開発工程の設計を定める。実装済みの機能は [README](../README.md)、操作方法とツール設定は[開発手順](development.md)、外部仕様と測定根拠は[技術資料](#根拠資料)を参照する。製品の公開契約を固定するための決定事項は[第13節](#13-詳細仕様の確定項目)にまとめる。

## 1. 目的と対象範囲

プロジェクトごとに開発用スクリプトの言語や要件が異なっても、質問、確認、状態、結果の読み方は統一できる。hamio は表示処理の重複を減らし、利用者が操作を理解する負担と開発者が UI を保守する負担を抑える。

| 項目       | 方針                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 利用言語   | Shell、Python、Go、TypeScript などからプロセス I/O と JSON で接続する    |
| 実装       | Bun + TypeScript で UI と公開契約の処理を実装する                        |
| 配布       | Bun を同梱する実行ファイルを macOS / Linux 向けに提供する                |
| 利用環境   | hamio の UI を使うために Bun・Nix の導入を要求しない                     |
| 対話と表示 | フォーム、選択、確認、秘密入力、メッセージ、表、進捗、結果、エラーを扱う |
| 機械利用   | 非対話入力と構造化出力を提供し、装飾と不要な反復を抑える                 |
| 品質       | 安全性、起動、応答、メモリ、CPU、出力量、業務への追加負荷を検証する      |
| 開発       | Nix、ローカル検査、Git hooks、PR 検査、端末プレビューで変更を確認する    |

初期リリースの対象はローカルのターミナル UI とする。Web UI、常駐サービス、ネットワーク API、任意コードを実行するプラグイン、汎用ワークフロー言語、自由なテーマ、全画面ダッシュボード、自己更新は含めない。

製品の対応 CPU、最低 OS、Linux libc は配布物の実機検証で確定する。開発用 Nix shell の対応環境を、そのまま製品の動作保証範囲にはしない。

## 2. 用語と責務

| 用語       | 意味                                                                         |
| ---------- | ---------------------------------------------------------------------------- |
| 利用側     | hamio を呼び出すスクリプトと、それを管理するプロジェクト                     |
| 業務処理   | API 呼び出し、ビルド、Git 操作、ファイル変更など、スクリプトが行う本来の処理 |
| 入力定義   | 質問の項目、型、制約、ラベル、選択肢を表すデータ                             |
| 公開契約   | 利用側と hamio が共有する入出力データと動作規則                              |
| run        | 利用側スクリプトによる一回の業務実行                                         |
| task       | run 内で開始・進捗・完了・失敗を識別する処理単位                             |
| event      | task の状態変化などを通知する一件のデータ                                    |
| 連続表示   | 一つの表示プロセスが event を受け取り、進捗と結果を更新する利用方法          |
| 描画       | 入力や状態のモデルから、表示文字と端末制御命令を生成する処理                 |
| 機械モード | 対話待ちと端末装飾を使わず、構造化データを返す動作                           |
| プレビュー | 開発中の端末出力を記録し、PR とチャットで確認する画像・録画                  |

利用側は業務の実行、順序、並列数、権限、再試行、取り消しを管理する。業務に必要な Python、Git、利用側の TypeScript 実行環境も利用側が用意する。同梱する Bun は hamio 自身の UI を動かすために使用する。

| 利用側が管理するもの             | hamio が管理するもの                       |
| -------------------------------- | ------------------------------------------ |
| 質問の内容、選択肢、値           | 入力部品と表示規則                         |
| API 照会などを伴う業務上の妥当性 | 型、必須条件、範囲などの基本入力検証       |
| 業務の実行と task の状態         | 通知の受信、表示状態への反映、描画の集約   |
| 秘密値の供給と秘密項目の指定     | 指定された秘密値の表示・ログへの漏えい抑制 |
| 回答後の業務判断                 | 回答、不足入力、検証失敗、キャンセルの返却 |
| スクリプト全体の成否             | UI 自体の成功、失敗、中断の通知            |

## 3. 実行構成

利用側は hamio を独立プロセスとして起動し、明示した入出力経路で JSON を交換する。配布する実行ファイルには hamio 本体、UI の依存コード、Bun ランタイムを含める。プロセスの境界で実装言語を分離し、公開契約によって UI ライブラリの変更から利用側を保護する。

```mermaid
flowchart LR
    U["利用側スクリプト"]
    B["業務処理<br/>API・Git・ファイル・並列実行"]
    C["hamio<br/>CLI・JSON の受け付け"]
    M["入力検証・状態管理"]
    H["人向け UI<br/>フォーム・表・進捗"]
    R["構造化した返却値<br/>回答・結果・エラー"]
    U --> B
    U -->|入力定義・event・結果| C
    C --> M
    M --> H
    H -->|回答・キャンセル| M
    M --> R
    R --> U
```

内部の責務は、公開契約の受け付け、入力検証と状態管理、人向け描画、構造化出力に分ける。同じ実行ファイル内で構成し、モジュール分割のために別サービスや常駐プロセスを設けない。

フォームと段階表示の UI 基盤は Clack を第一候補とする。日本語表示、端末復旧、Bun 同梱時の動作、性能予算を採用条件とし、表や共通出力の依存も機能、保守、配布コストで評価する。ライブラリ固有の関数や設定は内部の変換層で扱い、利用側へ公開しない。

## 4. 利用方法とライフサイクル

### フォーム

利用側は関連する質問を一つの入力定義として渡す。hamio はフォーム単位で入力を扱い、回答完了、キャンセル、不足入力、検証失敗を区別して返す。質問ごとのプロセス起動は行わない。

回答を業務へ適用できるかは利用側が判断する。たとえば接続先の選択後に利用側が接続可否を確認し、不成立なら理由を添えて再質問する。入力定義に任意の関数や実行コマンドを含める経路は設けない。

### 単発表示

利用側はメッセージ、表、結果の内容と意味を渡す。hamio は指定された形式で表示して終了する。成功、警告、秘密といった区分は公開契約で指定し、自由文から推測させない。

### 連続表示

利用側は run の通知を一つの経路へ集約する。表示期間中は同じ hamio プロセスを使用し、task や event の件数に応じて UI プロセスを増やさない。

状態には開始、進捗、完了、失敗を持たせる。EOF は入力経路の終了として扱い、業務成功を表す通知とは分ける。利用側は業務結果と UI の終了状態の両方を受け取り、スクリプト全体の終了コードを決める。

### 端末の共有と中断

一つの端末を描画する主体は一つとする。連続表示中にフォームが必要な場合、利用側が端末の使用を切り替える。停止・再開または終了による切り替え規則は公開契約で定める。

同時に有効な質問は一つとする。回答を必要としない業務処理は並行して進められる構成にする。キャンセル時は入力モードと表示状態を復旧し、成功と区別して返す。業務を停止・継続・再実行する判断は利用側に残す。

## 5. 公開契約

入出力には [RFC 8259](https://datatracker.ietf.org/doc/html/rfc8259) に基づく JSON を使用する。公開するのは質問、回答、状態、結果の意味であり、関数、クラス、Bun 固有オブジェクトを受け渡さない。

| データ     | 含める情報                                                    |
| ---------- | ------------------------------------------------------------- |
| 入力定義   | 契約版、項目 ID、入力型、必須条件、制約、ラベル、説明、選択肢 |
| 回答       | 項目 ID と値、回答完了・キャンセル・不足・検証失敗の状態      |
| 表示 event | task ID、順序を識別する情報、種別、状態、表示データ           |
| 業務結果   | 成否、結果データ、警告、省略の有無                            |
| UI エラー  | 安定したエラーコード、対象項目、説明、返却結果の有無          |

入力部品の範囲は text、confirm、select、multiselect、secret とする。出力部品の範囲は message、key-value、table、progress、result、error とする。これらは部品の意味を表す名称であり、CLI や JSON の具体的な綴りは詳細仕様で固定する。

項目 ID と選択肢の値は表示ラベルから独立させる。入力制約と表示順・説明も分ける。JSON Schema を使用する場合は対応する制約を列挙し、未対応の制約を拒否する。外部参照をネットワークから自動取得しない。

実行ファイルと公開契約は別々に版を管理する。未知の major 版は UI 操作前に拒否し、任意項目の追加と必須動作の変更に互換性の規則を設ける。機能照会は必要な範囲だけを選択できる形式にする。

入力不正、UI 障害、キャンセル、業務失敗は別の状態とする。古い進捗、重複、順序違反、中断後の event の扱いを定め、異なる run の状態を混在させない。大きな整数、日時、バイト列の表現は利用言語間で値が一致することを確認する。

## 6. 対話と出力の規則

人向け UI と機械向け出力は、共通の入力・状態・結果モデルから生成する。出力形式、対話の可否、色・端末制御の可否を独立した設定として扱い、明示指定を優先する。TTY はストリームの接続先を調べる情報であり、人と AI エージェントの識別には使わない。

| 項目   | 人向け UI                      | 機械モード                                  |
| ------ | ------------------------------ | ------------------------------------------- |
| 入力   | 端末のフォームで受け付ける     | 事前指定値を検証し、不足項目を返す          |
| 進捗   | 更新を集約して描画する         | 既定は最終結果。要求時に必要な event を返す |
| 結果   | 表や説明で示す                 | 安定したキーの JSON を返す                  |
| エラー | 原因と対処を示す               | コード、対象項目、説明、結果状態を返す      |
| 装飾   | 端末能力と設定に従う           | ANSI 制御、spinner、カーソル操作を使わない  |
| 中断   | 端末を復旧してキャンセルを返す | 成功と区別した状態と終了コードを返す        |

端末 UI は stderr、フォーム回答と機械向け結果は stdout を基本経路とする。回答用の stdout は利用側が捕捉する。機械モードでは stderr も管理し、ライブラリの描画や不要な診断を混在させない。

フォーム定義とキー入力には別の経路を用意する。たとえば定義ファイルを明示し、stdin でキーを受け、stdout に回答を返す。連続表示は stdin を event の入力に使う。非対話モードでは不足入力を返し、`/dev/tty` を開いて回答を待たない。

機械向け出力では重複進捗、不要な説明、全スキーマの反復を抑える。大量データは項目と範囲を選択可能にし、省略件数と続きの取得方法を示す。重要な警告、失敗、不足入力、機械向けの値を黙って切り捨てない。

token 消費は stdout・stderr の合計を対象に、エージェントの取得方法と tokenizer を指定して測定する。JSON の採用だけを削減効果の根拠にはしない。

## 7. 性能設計

hamio は利用側のビルドやテストと CPU・メモリを共有する。性能評価には UI 本体だけでなく、利用側の JSON 生成、転送、待機、補助プロセスによる負荷を含める。

### 並列処理

業務の並列数と依存関係は利用側が制御する。複数 task の通知は一つの送信経路にまとめ、複数の送信元が同じ pipe へ JSON のバイト列を直接書き込まない。業務の更新ごとに描画完了を待たせない構成とする。

hamio の I/O は非同期に待ち、同時受付数と待ち行列に上限を設ける。CPU 負荷は入力規模、アルゴリズム、処理単位を含めて評価する。Worker は生成・転送・状態保持・終了まで含めて効果がある場合に採用し、既定で全 CPU コアを占有する構成を避ける。

非同期 I/O と CPU の並列実行は区別する。UI 単体の応答に加え、業務処理と同時実行した場合の業務所要時間も測定する。

### 保持量と描画頻度

受信フレーム、文字列、階層、待ち行列の件数・バイト数、活動中 task、ログ、表に個別の上限を設ける。連続入力は上限付きのフレームとして処理し、全入力を巨大な JSON として保持・解析しない。

進捗は task ごとの最新状態に集約する。完了 task の詳細は用途に応じて解放し、ログと表は表示範囲を限定する。全件の集計、並べ替え、続きの取得は利用側の責務とする。

進捗の再描画には頻度上限を設け、状態が変わらない再計算を抑える。入力応答、エラー、完了は進捗の描画周期と分けて扱う。機械モードでは描画とアニメーション用 timer を起動せず、待機中の繰り返し処理を抑える。

### 混雑時の扱い

受信と描画を分け、出力先が遅い場合はデータの重要性に従って集約、待機、エラー返却を行う。有限メモリで、すべての通知を保持しながら無制限に受け付ける設計にはしない。

| データ               | 混雑時の規則                                                         |
| -------------------- | -------------------------------------------------------------------- |
| 途中の進捗           | 最新状態へ置換する。利用側でも可能な範囲で JSON 化前に集約する       |
| 詳細ログ             | 最近の一定量を保持し、省略件数を通知する。全件保存は利用側が管理する |
| 完了・失敗・重要警告 | 受付・配送の失敗を識別し、待機上限を超えたら明示的なエラーを返す     |
| 入力要求・回答       | 取得・返却の失敗を成功や肯定へ置き換えない                           |

UI 障害時の業務継続は利用側が判断する。待ち行列の上限と待機時間は代表データを用いて詳細仕様として固定する。

### 暫定性能予算

以下は初期リリースの設計目標であり、実測値ではない。基準機、OS、端末、Bun 版、入力データを定め、配布用実行ファイルで判定する。

| 指標                   | 目標                                    | 測定条件                                                                                          |
| ---------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 小さい機械向け呼び出し | 起動から結果取得まで p95 100 ms 以内    | 入出力各4 KiB以下。OS cache が温まった状態で新規起動し、cold start は別記する                     |
| 入力応答               | キー入力から表示反映まで p95 50 ms 以内 | 日本語を含む通常フォーム。業務処理と人の思考時間を除く                                            |
| メモリ                 | 定常 RSS 64 MiB、peak RSS 128 MiB 以内  | 1 run、100 task以内、最近のログ2,000行以内・各行1 KiB以内。補助プロセスを含む同時使用量も評価する |
| 業務への追加時間       | hamio なしの対照に対して5%以内          | 対照は5秒以上。同じ業務結果・並列数、人の入力待ちなし。短い処理は絶対追加時間も評価する           |
| 待機中の CPU           | 1 core換算で平均1%以下                  | 新着 event・アニメーションのない30秒区間                                                          |

p95 は応答の95%が収まる時間を指す。中央値、p95、試行数、ばらつきを記録し、外部 API の変動や人の操作時間を分けて扱う。

JS heap とプロセス全体のメモリを分けて観測する。RSS、共有ページを按分する PSS、macOS の phys_footprint は異なる尺度として、API・単位・OS を記録する。footprint を RSS の予算に代入せず、Worker のメモリを二重加算しない。複数プロセスの RSS 合計は専有物理メモリと同一ではない。

アプリ内の保持量上限と OS による厳密なメモリ制限は別に扱う。省メモリ設定、bytecode、Worker は一条件ずつ比較し、起動、応答、メモリ、CPU の改善と悪化を併記する。予算未達時は構成、依存、描画方式、必要に応じてランタイムを見直す。予算変更には利用シナリオと測定根拠を残す。

## 8. セキュリティ設計

保護対象は開発マシン、利用側コード、認証情報、入力値、端末、配布物とする。入力定義、表示文字列、ログ、ファイル名、依存コード、ビルド資産を検証する。所有者のスクリプトが取得した値でも、外部由来のデータは未信頼入力として扱う。

### 入力と秘密情報

入力の型、サイズ、深さ、件数を検証する。外部文字列の端末制御命令を無害化し、描画では hamio が生成した命令だけを使用する。色用の SGR に加え、端末が解釈する他の命令も対象にする。

機械出力は JSON としてエスケープする。表示用の省略や無害化によって返却値を黙って変更しない。UI 定義から Shell、JavaScript、外部プラグインを実行する経路は設けない。

秘密項目は利用側が指定する。回答は呼び出し元が捕捉する経路で返し、端末への直接表示、復唱、エラー、ログ、永続化への混入を防ぐ。自由文中の秘密を完全に自動検出する保証は持たせない。

回答の返却経路には秘密の実値が存在するため、受信後の保管、ログ、エージェントへの転送は利用側が管理する。表示マスク、暗号化、権限分離はそれぞれ別の保護とする。

### 実行環境

通常の UI 利用はオフラインで完結させる。必要なコードを配布物に含め、Bun の暗黙の `.env`・`bunfig.toml` 読み込みをビルド設定で無効化する。実行時に依存を自動取得しないことも検証する。

起動前に作用する `BUN_OPTIONS` や `BUN_BE_BUN` は固定した Bun 版で確認する。アプリ開始後の検査だけで起動環境の影響を排除できるとは扱わない。

hamio は利用者と同じ OS 権限で動く。独立プロセスとランタイム同梱は sandbox を提供しない。削除やデプロイの許可、業務の安全性、子孫プロセスの停止は利用側が管理する。

## 9. 開発環境と品質検査

開発ツールは `flake.nix` と `flake.lock`、JS 依存は `package.json` と `bun.lock` で固定する。Bun は TS スクリプトとテストを、Node.js は開発用ツールを実行する。開発環境は利用者向け配布物から分離する。

Nix shell の対応 system は `aarch64-darwin`、`aarch64-linux`、`x86_64-linux` とする。ローカルと CI は同じ定義と lockfile を使う。依存取得と hooks 導入は明示的なセットアップで行い、shell への入場だけでは実行しない。通常の依存取得は lockfile を変更せず、lifecycle scripts を実行しない。

| 工程      | 検査と確認                                                                    |
| --------- | ----------------------------------------------------------------------------- |
| 編集      | 保存時の format、型診断、対象のテストを利用する                               |
| UI 確認   | 専用 shell でプレビューを生成し、画像と必要な録画を確認する                   |
| commit 前 | ステージ済みファイルを検査し、部分ステージを保持する。同時タスクは2に制限する |
| push 前   | 作業ツリー全体の Lint、format、型、テスト、プレビューの更新漏れを検査する     |
| PR        | Linux の1ジョブで全体検査、Nix 定義評価、検査前後の差分確認を行う             |

format は TS・JS・JSON を Biome、Markdown・YAML を Prettier、Nix を nixfmt、Shell を shfmt に統一する。ShellCheck と actionlint で Shell と workflow を検査する。TypeScript は strict 設定とし、宣言ファイルも型検査する。

Git hooks と検査コマンドはソースを自動修正しない。修正用コマンドを明示的に実行し、差分を確認してステージする。pre-push は未コミットの内容も検査するため、GitHub 上のマージ候補は PR で別途検証する。

CI の自動トリガーは `master` 向け PR の作成・更新・再開とする。push と PR close は対象外とし、変更は PR で検証する。macOS は関連変更時に手動で同じ検査を実行する。Bun・Nix・hooks・OS に関わる依存を変更した場合は macOS の確認を行う。製品の端末 I/O、プロセス管理、配布物を実装する際は、両 OS の実行テストを自動化する範囲を定める。

`.agents/skills` に設計、TypeScript、性能の判断基準を置き、`AGENTS.md` を入口とする。スキルは作業に必要な領域だけ読む。開発基盤の検査、各 OS の動作試験、製品の性能判定はそれぞれ独立して実施する。

## 10. 端末 UI のプレビュー

UI の変更は実際の疑似端末で実行し、代表状態の PNG と操作の録画でレビューする。プレビューの生成と共有は開発工程の一部であり、利用者向け製品の機能や依存には含めない。

シナリオは実行コマンド、端末サイズ、待つ出力、送るキー、撮影する状態を定義する。Bun の PTY で出力を記録し、agg が ANSI とカーソル操作を解釈して描画する。Pillow が静止画を PNG に変換する。端末出力を別実装の画面に置き換えない。

描画ツールとフォントは専用の Nix shell に固定する。生成は明示的なコマンドで行い、通常の hooks と CI では生成元と PNG の hash を照合する。画像生成を日常の全体検査へ組み込まず、短いフィードバックを保つ。

代表 PNG と生成元の記録はソースと一緒に版管理する。PR 本文には対象 commit SHA に固定した画像リンクを埋め込み、チャットには同じ PNG をインライン表示する。録画は必要な操作の確認に用い、出力全文をチャットへ転記しない。

録画にはダミーデータを使用する。子プロセスの環境変数を限定し、時間、出力量、event 件数、描画処理に上限を設ける。生成物は公開資料として内容を確認し、外部サービスへ自動送信しない。

製品の表示確認では製品の入口を呼ぶ。録画基盤の検証用プログラムである fixture は、その用途を画像と文書に明記する。hash の一致は更新漏れを検出するための条件であり、目視確認の代わりにはならない。固定した端末エミュレーターでの再描画は、各 OS の端末動作や製品性能の検証とも区別する。

## 11. リポジトリ・配布・保守

### 公開リポジトリ

リポジトリ `9uiLe/hamio` は公開し、変更権限を所有者に限定する。第三者の一般投稿を受け付けない運用とし、GitHub の投稿・レビュー制限を適用する。期限付き制限は失効前に見直す。公開リポジトリの閲覧、clone、fork は許容する。

CI は所有者の操作を対象とし、PR は同一リポジトリを送信元とするものだけを検査する。`pull_request_target` は使用しない。トークンは読み取り権限のみとし、checkout 後に認証情報を保持しない。第三者のコードを無条件に実行したり配布物へ含めたりしない。

検査成功をマージ条件にする場合は、GitHub の branch ruleset で必須チェックを設定する。ローカル hooks、workflow の起動条件、GitHub のマージ制限は別の仕組みとして扱う。

### 配布物と検証

製品は OS・CPU 別の実行ファイルとして GitHub Releases で配布する。版、対応環境、checksum、ビルドの由来を示す provenance、部品とライセンス情報を添付する。公開後のタグと資産を固定する immutable releases を使用する。

| 対象         | 固定・追跡する情報                                         |
| ------------ | ---------------------------------------------------------- |
| ツールと依存 | Nix 入力、Bun 版、JS 依存の lockfile                       |
| CI           | Actions と再利用 workflow の完全な commit SHA              |
| 生成物       | ソース commit、ビルド設定、バイナリ hash                   |
| 配布元       | `9uiLe/hamio`、公開 workflow、ソース ref / commit          |
| SBOM         | JS 依存、同梱 Bun/runtime、native 部品、取得元、ライセンス |

配布候補は Bun・Nix のない環境で検証し、実行時の `/nix/store` 依存とネットワーク取得がないことを確認する。開発 shell の固定、配布ビルドの隔離、バイト単位の再現性は別々に検証する。配布ビルドを Nix derivation で定義するかは詳細仕様で確定する。

checksum で完全性を、provenance で配布元とビルド工程を確認する。検証ツールの取得経路も定める。SBOM は出荷物の部品一覧として照合し、同梱ランタイムや native 部品の記載漏れを調べる。依存固定、脆弱性検査、SBOM、provenance を組み合わせて評価する。

### 更新と脆弱性対応

ビルド権限と公開権限を分離し、公開権限は必要な工程だけに付与する。依存更新は取得元と差分を確認し、通常更新と緊急セキュリティ更新の手順を定める。同梱 Bun の脆弱性には hamio の再配布で対応する。

利用者は版を選択して明示的に更新する。検証に失敗した配布物は実行・置換せず、バックグラウンドの自己更新を行わない。保守には影響版の告知、修正版の公開、非公開の脆弱性報告窓口を含める。

## 12. リリースの受け入れ条件

製品のリリース判定には配布用実行ファイルを使用する。開発時の TS 直接実行、ツール導入、プレビュー生成の時間を製品性能の結果に混ぜない。

| 対象         | 受け入れ条件                                                                            |
| ------------ | --------------------------------------------------------------------------------------- |
| 開発基盤     | 固定したツールと lockfile でローカル・CI の検査を再現できる                             |
| プレビュー   | 実行対象とシナリオを識別でき、生成元と画像が一致し、代表状態を目視確認できる            |
| 配布物       | Bun・Nix なしで動作し、通常 UI が依存取得や `/nix/store` を必要としない                 |
| 多言語       | Shell・Python の回答・結果・エラーが一致し、Go・TS も標準プロセス I/O で接続できる      |
| 端末         | 日本語幅、emoji、狭い幅、resize、色なし表示、Ctrl-C、EOF、入力モードの復旧が機能する    |
| 機械モード   | 対話待ちと端末制御がなく、人向け UI と同じ値・業務状態を返す                            |
| 出力量       | 成功・失敗・不足入力・大量出力の byte と token を比較し、重要情報を保持する             |
| 性能         | 基準環境で暫定性能予算を評価し、利用側の JSON 生成・転送を含む追加負荷を記録する        |
| 並列・長時間 | 業務並列数と同時 run 数を変え、業務への影響、完了 task の累積、保持量を確認する         |
| 混雑・中断   | 大量 event、遅い端末・pipe、閉じた出力先で無期限待機や重要通知の黙った喪失がない        |
| 入力保護     | 巨大・不正 JSON、深い構造、制御文字、秘密を含むエラーを安全に扱う                       |
| 配布検証     | 改ざん、別 repository/workflow、想定外 commit の資産を拒否し、SBOM を出荷物と照合できる |

測定記録にはソース commit、Nix 入力、Bun 版、ビルド設定、hash、CPU、RAM、OS、端末、負荷状態、測定 API、単位、試行数を含める。通常測定と profile・強制 GC を伴う診断を分ける。

代表データと結果を回帰検知に用い、Bun、UI 依存、配布方式の変更時に再検証する。同じ業務を hamio なし・ありで比較し、UI 単体と業務全体の両方を評価する。
