# hamio 基本設計

hamio は、開発用スクリプトの入力フォームと出力を統一するターミナル UI ツールである。スクリプトは業務処理を実行し、hamio は質問、回答、進捗、結果を共通の形式で扱う。利用側の実装言語を問わず、人には操作しやすい UI を、AI エージェントや CI には必要な情報に絞った構造化データを提供する。

本書は製品の責務、公開契約、性能、安全性、開発・配布の基本方針を定める。実装状況は [README](../README.md)、開発作業は[開発環境と検査](development.md)を参照する。公開契約の固定と製品リリースに必要な詳細仕様は、第13節に示す。

## 1. 製品の目的と範囲

開発用スクリプトはプロジェクトごとに言語、機能、実行環境が異なる。入力方法や表示規則まで個別に実装すると、利用者は操作を覚え直す必要があり、開発者は表示処理を重複して保守することになる。hamio は業務処理の自由度を保ちながら、利用者との接点を共通化する。

対象とする用途は、設定値の収集、実行対象の選択、操作前の確認、処理の進捗、警告、結果の一覧である。利用側は表示する内容と意味を渡し、hamio が入力の受け付けと表示を担当する。

| 要件                 | 設計方針                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| 多言語での利用       | Shell、Python、Go、TypeScript などから CLI と JSON で接続する                                      |
| 利用環境             | Bun を同梱した実行ファイルを macOS / Linux 向けに配布する。UI の利用に Bun・Nix の導入を要求しない |
| 操作と表示           | フォーム、選択、確認、秘密入力、メッセージ、表、進捗、結果、エラーを統一する                       |
| AI エージェントと CI | 非対話入力と構造化出力を提供し、不要な描画・反復出力を抑える                                       |
| 性能                 | 起動、入力応答、メモリ、CPU、業務への追加時間をリリース条件として評価する                          |
| セキュリティ         | 入力、秘密情報、端末制御、依存取得、ビルド、配布物に検証と権限制御を設ける                         |
| 開発工程             | Nix でツールを固定し、編集時・commit 前・push 前・PR 時に問題を検出する                            |

業務処理の実行、順序、並列数、権限、再試行、取り消しは利用側が管理する。Python、Git、利用側の TypeScript を実行するランタイムなど、業務に必要なツールも利用側が用意する。hamio に同梱する Bun の役割は hamio 自身の UI を動かすことである。

初期リリースはローカルのターミナル UI を対象とする。Web UI、常駐サービス、ネットワーク API、任意コードを実行するプラグイン、汎用ワークフロー言語、自由なテーマ、全画面ダッシュボード、自己更新は対象外とする。配布物の CPU、最低 OS、Linux libc の対応範囲は実機検証を条件に確定する。

## 2. 用語

| 用語       | 意味                                                                      |
| ---------- | ------------------------------------------------------------------------- |
| 利用側     | hamio を呼び出すスクリプトと、それを管理するプロジェクト                  |
| 業務処理   | API 呼び出し、ビルド、Git 操作、ファイル変更など、利用側が行う本来の処理  |
| 入力定義   | 質問の項目、型、制約、ラベル、選択肢を記述するデータ                      |
| 公開契約   | 利用側と hamio が共有する入出力データと動作規則の仕様                     |
| run        | 利用側スクリプトによる一回の業務実行                                      |
| task       | run の中で開始・進捗・完了・失敗を識別する処理単位                        |
| event      | task の状態変化などを通知する一件のデータ                                 |
| 連続表示   | 同じ表示プロセスが複数の event を受け取り、進捗と結果を更新する利用方法   |
| 描画       | 入力や状態のモデルから、端末へ表示する文字と制御命令を生成する処理        |
| 機械モード | 対話待ちと端末装飾を使わず、AI エージェントや CI へ構造化データを返す動作 |

## 3. 全体構成と責務

hamio 本体は Bun + TypeScript で開発する。配布物には本体、UI の依存コード、Bun ランタイムを含める。利用側は独立プロセスとして hamio を起動し、標準入出力などの明示した経路で JSON を交換する。この境界により、利用側の言語と hamio 内部の UI ライブラリを独立して選べる。

```mermaid
flowchart LR
    U["利用側スクリプト"]
    B["業務処理<br/>API・Git・ファイル・並列実行"]
    C["hamio<br/>CLI・JSON の受け付け"]
    M["入力検証・状態管理"]
    H["人向け UI<br/>フォーム・表・進捗"]
    R["構造化した返却値<br/>回答・結果・エラー"]
    U --> B
    U -->|入力定義・event・結果| C
    C --> M
    M --> H
    H -->|回答・キャンセル| M
    M --> R
    R --> U
```

内部は、公開契約の受け付け、入力検証と状態管理、人向け UI、構造化出力に分ける。これらは同じ実行ファイルに含め、モジュール分割のために別サービスや常駐プロセスを設けない。

| 利用側の責務                         | hamio の責務                               |
| ------------------------------------ | ------------------------------------------ |
| 業務の実行、対象環境、権限           | 入力部品と表示規則                         |
| 質問の内容、選択肢、値               | 型、必須条件、範囲などの基本入力検証       |
| API 照会などを伴う業務上の妥当性検証 | 回答、不足入力、検証失敗、キャンセルの返却 |
| 処理順序、並列数、再試行、取り消し   | task の通知の受信と表示への集約            |
| 秘密値の供給と秘密項目の指定         | 指定された秘密値の表示・ログへの漏えい抑制 |
| 業務結果とスクリプト全体の終了コード | UI 自体の成功・失敗・中断の通知            |

公開契約は質問、状態、結果の意味を表す。UI ライブラリ固有の設定は内部の変換層で扱い、ライブラリの変更を利用側へ波及させない。

入力と段階表示の UI 基盤は Clack を第一候補とし、日本語表示、端末復旧、Bun 同梱時の動作、性能予算を採用条件とする。表や共通出力の追加依存は、必要な機能と保守・配布コストを評価して選ぶ。独立コマンドによる連携と実行ファイル生成の根拠は、[UI と言語間連携](research/ui-and-integration.md)および[ランタイムの技術資料](research/runtime-and-supply-chain.md)に示す。

## 4. 利用方法とライフサイクル

### フォーム

利用側は関連する質問を一つの入力定義として渡す。hamio は回答完了、キャンセル、不足入力、検証失敗を区別して返す。質問ごとにプロセスを起動せず、フォーム単位で入力を扱う。

回答の業務上の妥当性は利用側が確認する。たとえば選択した環境への接続可否を利用側が調べ、不成立なら理由を付けて再質問する。入力定義に任意の関数やコマンドを含めることはできない。

### 単発表示

利用側はメッセージ、表、結果などを意味のあるデータとして渡す。hamio は指定された形式で出力して終了する。成功、警告、秘密といった区分は公開契約で指定し、自由文から推測させない。

### 連続表示

利用側は run ごとの通知を一つの経路へ集約し、表示期間中は同じ hamio プロセスを使う。task や event の数に応じて UI プロセスを増やさない。

開始、進捗、完了、失敗を明示的な状態として扱う。入力が終わったことを示す EOF は業務成功を意味しない。利用側は業務結果と hamio の終了状態を確認し、スクリプト全体の成否を決める。

### 端末の共有と中断

一つの端末へ描画する主体は一つとする。連続表示中にフォームが必要になった場合、利用側が端末の使用をフォームへ切り替える。停止・再開または終了による切り替え方式は公開契約で定める。

同時に有効な質問は一つとし、その回答を必要としない業務処理は並行して進められるようにする。キャンセル時は入力モードと表示状態を復旧し、成功とは異なる結果を返す。業務の停止や継続、再実行の判断は利用側が行う。

## 5. 公開契約

入出力は [RFC 8259](https://datatracker.ietf.org/doc/html/rfc8259) に基づく JSON で表現する。関数、クラス、Bun 固有オブジェクトを受け渡さず、すべての利用言語で同じ値と状態を扱える形式にする。

| データ     | 契約に含める情報                                              |
| ---------- | ------------------------------------------------------------- |
| 入力定義   | 契約版、項目 ID、入力型、必須条件、制約、ラベル、説明、選択肢 |
| 回答       | 項目 ID と値、回答完了・キャンセル・不足・検証失敗の状態      |
| 表示 event | task ID、順序を識別する情報、種別、状態、表示データ           |
| 業務結果   | 成否、結果データ、警告、省略の有無                            |
| UI エラー  | 安定したエラーコード、対象項目、説明、返却結果の有無          |

入力部品は text、confirm、select、multiselect、secret、出力部品は message、key-value、table、progress、result、error を初期範囲とする。これらは部品の意味を示す名称であり、CLI や JSON の具体的な綴りは公開契約の固定時に定める。

項目 ID と選択肢の値は、表示ラベルから独立した安定値にする。入力制約と表示順・説明を分離する。JSON Schema を用いる場合は対応する制約を列挙し、未対応の制約を拒否する。外部参照をネットワークから自動取得する経路は設けない。

実行ファイルの版と公開契約の版を分け、未知の major 版は UI 操作前に拒否する。任意項目の追加と必須動作の変更を区別し、互換性の規則を定める。機能照会は必要な範囲を選べる形式とし、通常実行に全スキーマの出力を伴わせない。

入力不正、UI 障害、利用者のキャンセル、業務失敗を別の状態として扱う。完了後の古い進捗、重複、順序違反、中断後の event に規則を設け、別 run の状態を混在させない。大きな整数、日時、バイト列は言語間の一致を確認して表現を定める。

## 6. 人向け UI と機械向け出力

人向け UI と機械向け出力は共通の入力・状態・結果モデルから生成する。表示形式、対話の可否、色・端末制御の可否は独立して設定できるようにし、明示指定を優先する。TTY は端末接続の情報として使い、利用者が人か AI エージェントかを判定する根拠にはしない。

| 項目   | 人向け UI                      | 機械モード                                      |
| ------ | ------------------------------ | ----------------------------------------------- |
| 入力   | 端末のフォームで受け付ける     | 事前指定値を検証し、不足項目を返す              |
| 進捗   | 更新を集約して描画する         | 既定は最終結果。要求時に必要な event を出力する |
| 結果   | 表や説明で示す                 | 安定したキーの JSON を返す                      |
| エラー | 原因と対処を示す               | コード、対象項目、説明、結果状態を返す          |
| 装飾   | 端末能力と設定に応じて使う     | ANSI 制御、spinner、カーソル操作を使わない      |
| 中断   | 端末を復旧してキャンセルを返す | 成功と区別した状態と終了コードを返す            |

端末 UI は stderr、フォーム回答と機械向け結果は stdout を基本経路とする。利用側は回答用の stdout を捕捉する。機械モードでは stderr も出力管理の対象にし、ライブラリ由来のアニメーションや診断ログを通常出力へ混在させない。

フォーム定義とキー入力には別の経路を用意する。たとえば明示したファイルから定義を読み、stdin でキーを受け、stdout に回答を返す。連続表示は stdin を event の入力に使う。非対話モードは不足入力を返し、`/dev/tty` を開いて回答を待たない。

機械向け出力では重複進捗、不要な説明、全スキーマの反復を抑える。大量データは項目と範囲を選択できるようにし、省略件数と続きの取得方法を示す。重要な警告、失敗、不足入力と、機械向けの値は黙って切り捨てない。

token 消費は実際の取得方式と tokenizer を指定し、stdout・stderr の総出力量で評価する。JSON 形式の採用だけを削減効果の根拠にしない。[端末と出力形式の根拠](research/ui-and-integration.md)

## 7. 性能設計

性能評価の対象は、hamio の導入によって業務に加わる時間と資源消費である。本体に加え、利用側の JSON 生成、転送、待機、連携用の補助プロセスを含めて測定する。

### 並列処理

業務の並列数と依存関係は利用側が制御する。複数 task の通知は一つの送信経路へまとめ、同じ pipe に複数の送信元が JSON のバイト列を直接書き込まない。業務の更新ごとに描画完了を待たせない構成にする。

hamio は I/O を非同期に待ち、同時受付数と待ち行列を制限する。CPU 負荷には入力規模、アルゴリズム、処理単位の調整で対処し、Worker は生成・転送・状態保持・終了まで含めた効果を測定して採用する。UI が既定で全 CPU コアを占有する構成は避ける。

非同期 I/O と CPU の並列実行は別に評価する。業務側のビルドやテストと資源を共有する条件でも、UI の応答と業務の所要時間を確認する。[Bun の性能特性](research/performance.md)

### 保持量と描画量

受信フレーム、文字列、階層、待ち行列の件数・バイト数、活動中 task、ログ、表に個別の上限を設ける。連続入力は上限付きのフレームとして処理し、全入力を一つの巨大な JSON として保持・解析しない。

進捗は task ごとの最新状態へ集約し、完了した task の詳細は表示用途に応じて解放する。表は表示範囲を限定する。全件の集計、並べ替え、続きの取得は利用側が担当する。

進捗の再描画には頻度上限を設け、値の変わらない状態の再計算を抑える。入力応答、エラー、完了は進捗の描画周期と分けて扱う。機械モードでは端末描画とアニメーション用 timer を起動せず、待機中の繰り返し処理を抑える。

### 混雑時の扱い

遅い出力先に対し、有限のメモリで全データを保持しながら無制限の送信を受け続けることはできない。受信と描画を分け、データの重要性に応じて集約、待機、エラー返却を行う。

| データ               | 出力先が遅い場合の規則                                               |
| -------------------- | -------------------------------------------------------------------- |
| 途中の進捗           | 最新状態へ置換する。利用側でも可能な範囲で JSON 化前に集約する       |
| 詳細ログ             | 最近の一定量を保持し、省略件数を通知する。全件保存は利用側が管理する |
| 完了・失敗・重要警告 | 受付・配送の失敗を識別する。待機上限を超えたら明示的なエラーを返す   |
| 入力要求・回答       | 取得・返却の失敗を成功や肯定へ置き換えない                           |

UI 障害時に業務を継続するかは利用側が決める。待ち行列の上限と待機時間は、代表データを用いた検証で詳細仕様として固定する。

### 暫定性能予算

以下は初期リリースの設計目標である。達成の判定には基準機、OS、端末、Bun 版、入力データを定め、配布する実行ファイルを測定する。数値は実測結果ではない。

| 指標                   | 暫定目標                                | 測定条件                                                                                               |
| ---------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 小さい機械向け呼び出し | 起動から結果取得まで p95 100 ms 以内    | 入出力各 4 KiB 以下。OS cache が温まった状態で毎回新規起動し、cold start は別記する                    |
| 入力応答               | キー入力から表示反映まで p95 50 ms 以内 | 日本語を含む通常フォーム。業務処理と人の思考時間を除く                                                 |
| メモリ                 | 定常 RSS 64 MiB、peak RSS 128 MiB 以内  | 1 run、100 task 以内、最近のログ 2,000 行以内・各行 1 KiB 以内。補助プロセスを含む同時使用量も評価する |
| 業務への追加時間       | hamio なしの対照に対して 5% 以内        | 対照は5秒以上、同じ業務結果・並列数、人の入力待ちなし。短い処理は絶対追加時間も評価する                |
| 待機中の CPU           | 1 core 換算で平均 1% 以下               | 新着 event・アニメーションのない30秒区間                                                               |

p95 は測定した応答の95%が収まる時間を指す。中央値、p95、試行数、ばらつきを記録し、外部 API の変動や人の操作時間と hamio の追加時間を区別する。

JavaScript のヒープとプロセス全体のメモリを別々に観測する。RSS、共有ページを按分する PSS、macOS の phys_footprint は異なる尺度なので、取得 API・単位・OS を記録する。footprint を RSS の予算へ代入しない。同一プロセスの Worker 分を重複加算せず、複数プロセスの RSS 合計を専有物理メモリと同一視しない。

アプリ内の保持量上限と、プロセス全体の厳密なメモリ制限も区別する。測定 API の制約は[性能資料](research/performance.md#計測指標)を参照する。省メモリ設定、bytecode、Worker は一条件ずつ比較し、起動・応答・メモリ・CPU を合わせて評価する。予算未達時は構成、依存、描画方式、必要に応じてランタイムの選定を見直す。予算変更には利用シナリオと測定根拠を残す。

## 8. セキュリティ設計

保護対象は開発マシン、利用側コード、認証情報、入力値、端末、配布物である。入力定義、表示文字列、ログ、ファイル名、依存コード、ビルド資産を検証対象とする。所有者が実行するスクリプトでも、外部から取得した値は未信頼入力として扱う。

### 入力と秘密情報

入力の型、サイズ、深さ、件数を検証する。表示文字列に含まれる端末制御命令を無害化し、描画には hamio が生成した制御命令だけを使う。対策は色用の SGR に限定せず、端末が解釈する他の命令も対象にする。[端末制御と秘密情報](research/ui-and-integration.md#表示データと秘密情報)

機械出力は JSON としてエスケープし、表示用の省略や無害化によって元の値を黙って変更しない。UI 定義から Shell、JavaScript、外部プラグインを実行する経路は設けない。

秘密項目は利用側が指定する。秘密入力の回答は呼び出し元が捕捉する経路で返し、端末への直接表示、復唱、エラー、詳細ログ、永続化への混入を防ぐ。自由文に含まれる秘密の完全な自動検出は保証しない。

回答の返却経路には秘密の実値が存在する。受け取った値の保管、ログ、エージェントへの転送は利用側が管理する。表示マスクと、暗号化・権限分離は別の保護として扱う。

### 実行環境

通常の UI 利用はオフラインで完結させ、必要なコードを配布物に含める。Bun による暗黙の `.env`・`bunfig.toml` 読み込みはビルド設定で無効化し、実行時に依存を自動取得しないことを検証する。

起動前に作用する `BUN_OPTIONS` や `BUN_BE_BUN` は、固定した Bun 版で挙動を確認する。アプリ開始後のチェックだけで起動環境の影響を排除できるとは扱わない。[ランタイムの信頼境界](research/runtime-and-supply-chain.md#実行時の信頼境界)

hamio は利用者と同じ OS 権限で動作する。独立プロセスとランタイム同梱は任意コードを隔離する sandbox ではない。削除やデプロイの許可、業務の安全性、子孫プロセスの停止は利用側の責務とする。

## 9. 開発環境と品質検査

開発ツールは Nix の `flake.nix` と `flake.lock`、JavaScript 依存は `package.json` と `bun.lock` で固定する。Bun は TypeScript スクリプトとテストを実行し、Node.js は開発ツールを動かす。これらの開発環境と、利用者向けの配布物は別に管理する。

開発 shell は `aarch64-darwin`、`aarch64-linux`、`x86_64-linux` を対象とする。ローカルと GitHub Actions は同じ Nix 定義と lockfile を使う。導入する Nix の版、feature、取得経路、キャッシュの扱いは[開発手順](development.md)に定める。

依存取得と hooks 導入は明示的なセットアップで行う。Nix shell への入場だけでは JS 依存のインストールや Git 設定の変更を行わない。通常の依存取得では lockfile の変更と lifecycle scripts の実行を禁止する。

| 工程      | 検査と役割                                                                                         |
| --------- | -------------------------------------------------------------------------------------------------- |
| 編集      | Biome / Prettier による保存時 format と、TypeScript の型診断を利用する                             |
| commit 前 | Husky と lint-staged でステージ済みの対象を検査する。部分ステージを保持し、同時タスクを2に制限する |
| push 前   | 作業ツリー全体の Lint、format、型検査、テストを `bun run check` で実行する                         |
| PR        | macOS / Linux で同じ全体検査を行い、Nix 定義の評価と検査前後の差分も確認する                       |

TS・JS・JSON は Biome、Markdown・YAML は Prettier、Nix は nixfmt、Shell は shfmt で format を統一する。ShellCheck と actionlint で Shell と workflow を検査する。TypeScript は strict 設定を使い、宣言ファイルも型検査の対象に含める。

検査コマンドと Git hooks はソースを自動修正しない。修正用コマンドを明示的に実行し、差分を確認してからステージする。pre-push は未コミットの修正も含む作業ツリーを、PR の CI は checkout したマージ候補を検証する。ローカル hooks による検査と GitHub のマージ制限は別の仕組みである。

`.agents/skills` にはソフトウェア設計、TypeScript、パフォーマンスの判断基準を置き、`AGENTS.md` から参照する。スキルは必要な領域だけ読み、機械的な検査で判断できない責務・契約・計測条件の確認に使う。製品の性能予算は配布物の測定で判定する。

## 10. 配布と保守

製品は OS・CPU 別の実行ファイルとして GitHub Releases で配布する。版、対応環境、checksum、ビルドの由来を示す provenance、部品・ライセンス情報を添付し、公開後のタグと資産を固定する immutable releases を使用する。

| 対象           | 固定・追跡する情報                                              |
| -------------- | --------------------------------------------------------------- |
| ツールと依存   | Nix 入力、Bun 版、JS 依存の lockfile                            |
| CI             | Actions と再利用 workflow の完全な commit SHA                   |
| ビルドと生成物 | ソース commit、ビルド設定、バイナリ hash                        |
| 配布元         | `9uiLe/hamio`、期待する公開 workflow、ソース ref / commit       |
| SBOM           | JS 依存、同梱 Bun/runtime、追加 native 部品、取得元、ライセンス |

配布候補は Bun・Nix のない環境で検証し、実行時の `/nix/store` 依存とネットワーク取得がないことを確認する。Nix の開発 shell が固定されていることと、配布ビルドの隔離・バイト単位の再現性は別に検証する。配布ビルドを Nix derivation で定義するかは詳細仕様で確定する。

checksum で完全性を、provenance で配布元とビルド工程を確認する。検証ツールの入手経路も定める。部品一覧である SBOM は出荷物と照合し、同梱ランタイムや native 部品の記載漏れを確認する。依存固定、脆弱性検査、SBOM、provenance を組み合わせて検証し、どれか一つでコードの無害性が証明されるとは扱わない。

ビルドと公開の権限を分離し、公開権限は必要な工程だけに付与する。依存更新は取得元と差分を確認し、通常更新と緊急セキュリティ更新の手順を定める。同梱 Bun の脆弱性には hamio の再配布で対応する。

利用者は版を選んで明示的に更新する。検証に失敗した配布物は実行・置換せず、バックグラウンドの自己更新は行わない。影響版の告知、修正版の公開、非公開の脆弱性報告窓口を保守に含める。[配布機能と検証の根拠](research/runtime-and-supply-chain.md#配布物の検証)

## 11. 公開リポジトリの運用

リポジトリは公開し、変更権限を所有者に限定する。第三者の一般投稿を受け付けない方針とし、GitHub の投稿・レビュー制限を適用する。期限付きの制限には失効前の見直しを必要とする。

閲覧、clone、fork は公開リポジトリの利用として許容する。リポジトリを変更する権限とは区別し、第三者のコードを無条件に CI で実行したり配布物に含めたりしない。

品質検査 workflow は所有者の操作に限定し、PR は同一リポジトリを送信元とするものを対象にする。`pull_request_target` は使用せず、トークンは読み取り権限のみとし、checkout 後に認証情報を保持しない。workflow の検査結果をマージの必須条件とする場合は、GitHub の branch ruleset で別途管理する。

## 12. リリースの受け入れ条件

開発基盤の検査と製品のリリース判定を分ける。製品の検証には利用者へ配布する実行ファイルを使い、開発時の TypeScript 直接実行やツール導入時間を製品性能の結果に混ぜない。

| 対象         | 受け入れ条件                                                                            |
| ------------ | --------------------------------------------------------------------------------------- |
| 開発基盤     | 固定したツールと lockfile でローカル・CI の検査を再現できる                             |
| 配布物       | Bun・Nix なしで動作し、通常 UI が依存取得や `/nix/store` を必要としない                 |
| 多言語       | Shell・Python の回答・結果・エラーが一致し、Go・TS も標準プロセス I/O で接続できる      |
| 端末         | 日本語幅、emoji、狭い幅、resize、色なし表示、Ctrl-C、EOF、入力モードの復旧が機能する    |
| 機械モード   | 対話待ちと端末制御がなく、人向け UI と同じ値・業務状態を返す                            |
| 出力量       | 成功・失敗・不足入力・大量出力で byte と token を比較し、重要情報が保持される           |
| 性能         | 暫定性能予算を基準環境で評価し、利用側の JSON 生成・転送を含む追加負荷を記録する        |
| 並列・長時間 | 業務並列数と同時 run 数を変え、業務への影響、完了 task の累積、保持量を確認する         |
| 混雑・中断   | 大量 event、遅い端末・pipe、閉じた出力先で無期限待機や重要通知の黙った喪失がない        |
| 入力保護     | 巨大・不正 JSON、深い構造、制御文字、秘密を含むエラーを安全に扱う                       |
| 配布検証     | 改ざん、別 repository/workflow、想定外 commit の資産を拒否し、SBOM を出荷物と照合できる |

測定記録にはソース commit、Nix 入力、Bun 版、ビルド設定、hash、CPU、RAM、OS、端末、負荷状態、測定 API、単位、試行数を含める。通常測定と profile・強制 GC を伴う診断を分ける。

代表データと結果を回帰検知に使い、Bun、UI 依存、配布方式の変更時に再検証する。同じ業務を hamio なし・ありで比較し、UI 単体の速度と業務全体の負荷を両方評価する。
