# Preview の性能評価

Preview は、端末 UI の確認に使う開発機能である。本書では、生成物の再利用、端末からの再生成、読み取り専用の検査、Nix shell の準備にかかる時間を評価する。製品本体の起動・入力応答・メモリ予算は評価対象に含めない。

## 比較する構成

同じシナリオから同じ画像を得る二つの構成を比較する。

| 項目               | A: 常時生成構成                                   | B: 内容照合構成                                                                         |
| ------------------ | ------------------------------------------------- | --------------------------------------------------------------------------------------- |
| ソースの識別       | commit `e47e9e6df20084318f9940ae7aa6cd8f5a9cbc92` | [測定 JSON](preview-performance/after.json)の `sources` に対象ファイルの SHA-256 を記録 |
| 通常の呼び出し     | 画像の内容にかかわらず端末を実行して生成する      | 生成元と生成物の内容が一致すれば再利用し、不一致なら生成する                            |
| 強制生成           | 通常の呼び出しで毎回生成する                      | `--force` で毎回生成する                                                                |
| 入力前の閲覧用待機 | PNG・GIF とも500 ms                               | PNG は待機なし、GIF は500 ms                                                            |
| 録画の保持         | 撮影位置までの出力を画像ごとに複製する            | 一つの録画と撮影位置の event 番号を保持する                                             |
| PNG 変換           | 画像ごとに Pillow を起動する                      | 全画像を一つの Pillow プロセスで変換する                                                |
| Preview 関連テスト | 5件                                               | 再利用と録画の検証を含む7件                                                             |

B を Preview の設計として採用する。生成元の識別、再利用、強制生成の操作は[開発手順](../development.md#8-ターミナル-ui-のプレビュー)に記載する。両構成ともキャプチャと描画を順次実行し、agg の Rayon スレッドプールを2に設定する。

## 測定条件

- 測定日: 2026-09-17。
- macOS 26.2 / Darwin 25.2.0、Apple M1 Pro、10 core、RAM 16 GiB、arm64。
- Bun 1.4.2、同じ `flake.lock`・`bun.lock`、agg 1.9.0、同じ固定フォント・80列20行の疑似端末。
- シナリオは録画基盤の検証用プログラム `fixture` 一つ、静止画2枚、入力1回。両構成ともシナリオ内の350 msの進捗表示を含む。入力前の閲覧用待機は構成表のとおり。
- Nix store・依存・フォント取得済み。各条件を2回ウォームアップした後、新しい子プロセスで15回、直列に測定する。キャッシュ削除、強制 GC、プロファイラー、並列ベンチマークは使用しない。
- 通常のデスクトップ環境上で測定する。専用ベンチマーク機や他プロセスの完全停止は使用しない。初回のツール取得、電源状態による変動、Linux は評価対象外。
- 経過時間は測定側の `performance.now()`、CPU と maxRSS は終了後の `Subprocess.resourceUsage()` で取得する。CPU の報告値を microseconds から ms、maxRSS の報告値を bytes から MiB に換算する。maxRSS はプロセスツリー全体の同時 RSS 合計や macOS footprint ではない。[Bun の測定 API](https://bun.com/reference/bun/Subprocess/resourceUsage)、[時間の測定](https://bun.com/docs/project/benchmarking)

代表値は中央値とする。p95 は nearest-rank で計算し、15回ではサンプル最大値となる。小さな差を一般的な性能差と断定しない。生データは [A の測定](preview-performance/baseline.json)と [B の測定](preview-performance/after.json)に保存する。

## 経過時間

Nix shell 内の値は Bun の起動を含み、Nix shell の準備は含まない。「最新の PNG を確認」は、生成元と画像が一致する状態で通常の Preview コマンドを呼び出す反復操作である。A はその都度生成し、B は内容を照合して再利用する。端末から毎回生成する処理は「再生成」の行で比較する。

| 条件                             |    A 中央値 |    B 中央値 |       A p95 |       B p95 | 中央値の変化 |
| -------------------------------- | ----------: | ----------: | ----------: | ----------: | -----------: |
| 最新の PNG を確認、shell 内      | 1,174.15 ms |    15.26 ms | 1,185.14 ms |    15.82 ms |    98.7%短縮 |
| PNG を再生成、shell 内           | 1,174.15 ms |   606.82 ms | 1,185.14 ms |   627.46 ms |    48.3%短縮 |
| 最新の PNG・GIF を確認、shell 内 | 1,235.01 ms |    15.23 ms | 1,349.99 ms |    16.52 ms |    98.8%短縮 |
| PNG・GIF を再生成、shell 内      | 1,235.01 ms | 1,175.46 ms | 1,349.99 ms | 1,186.32 ms |     4.8%短縮 |
| 最新の PNG を確認、Nix 起動込み  | 1,952.97 ms |   775.33 ms | 2,008.49 ms |   858.36 ms |    60.3%短縮 |
| PNG を再生成、Nix 起動込み       | 1,952.97 ms | 1,428.78 ms | 2,008.49 ms | 1,534.92 ms |    26.8%短縮 |
| `bun run preview:check`          |    23.23 ms |    25.18 ms |    24.74 ms |    26.47 ms |  1.95 ms増加 |
| Preview 関連テスト               |   449.15 ms |   474.16 ms |   461.51 ms |   480.54 ms | 25.01 ms増加 |

通常の Preview コマンドでは、画像が最新なら B の再利用によって描画を省ける。端末から PNG を生成する場合も、閲覧用待機と変換処理を含む所要時間が48.3%短縮した。GIF の生成は閲覧用待機を含むため、短縮率は4.8%である。Nix shell 外からの呼び出しは環境の準備時間を含み、再利用の場合も約775 msを要した。

読み取り専用の `preview:check` に高速化は認められない。B は変更ファイルの診断と録画検証用の定義を含み、約2 ms長かった。関連テストは A が5件、B が7件であり、同一テストの速度比較ではなく、それぞれの保証を含む検査工程の所要時間である。

## CPU とメモリ

次の値は Nix shell 内で測定した中央値である。

| 条件              |     A CPU |     B CPU |  A maxRSS |  B maxRSS |
| ----------------- | --------: | --------: | --------: | --------: |
| 最新の PNG を確認 | 329.20 ms |  14.53 ms | 39.77 MiB | 19.97 MiB |
| PNG を再生成      | 329.20 ms | 255.69 ms | 39.77 MiB | 40.02 MiB |
| PNG・GIF を再生成 | 415.46 ms | 353.12 ms | 51.34 MiB | 51.50 MiB |

再利用では CPU とメモリの報告値も小さい。再生成は CPU が減った一方、maxRSS の改善は確認できず、約0.2 MiB大きかった。大量シナリオや長時間の録画に対するメモリ使用量は、この2枚の測定から推定しない。

## 内容照合構成の設計と検証

B は生成元と PNG の SHA-256 を照合し、最新なら再利用する。ファイルの更新時刻や存在だけでは判断しない。ローカル録画は生成元・GIF・端末出力の記録を専用の manifest で検証し、欠落・破損・古い内容を検出する。CI は PNG の読み取り専用チェックを行い、録画の生成を必要としない。

PNG の生成には閲覧用の500 ms待機を設けない。期待する出力への到達確認とシナリオ内の350 ms待機は実行する。録画データは一度だけ保持し、event 番号から各画像を描画する。Pillow は一つのプロセスで2枚の PNG を変換する。

入口、内容の照合、端末 I/O、描画は、それぞれの責務を持つモジュールとして構成する。利用者は通常の Preview コマンドを繰り返し使い、強制生成は `--force`、操作録画は `--recording` で指定する。更新チェックの失敗では、対象ファイルを最大10件と対処コマンドを表示する。

A と B が生成した2枚の PNG はバイト単位で一致した。日本語、入力画面、結果表の目視確認に加え、GIF の入力・進捗・結果を確認した。テストでは再利用時の非更新、描画ツールがない環境での再利用、生成元の追加・変更、画像改変、録画の欠落・改変、期待画面に到達しても終了しないプロセスを検証する。内容の照合は目視確認の代わりではない。

## 再計測

固定した描画環境で次を実行する。測定は生成物を更新するため、作業中の差分を確認し、測定後も差分をレビューする。通常の CI や hooks ではベンチマークを実行しない。

```sh
nix develop .#preview
bun scripts/benchmark-preview.ts dist/benchmarks/preview.json 15
```

`check`、`tests`、`generate`、`recording`、`wrapper`、`rebuild`、`rebuild-recording`、`wrapper-rebuild` の順に測る。B の `generate` と `recording` は2回のウォームアップで生成物が揃うため、測定対象は再利用である。`rebuild` は `--force` を付けて毎回端末から生成する。個別に測る場合は末尾にケース名を指定する。

```sh
bun scripts/benchmark-preview.ts dist/benchmarks/rebuild.json 15 rebuild
```

A を測定する場合は、構成表の commit を使う別 clone に[計測スクリプト](../../scripts/benchmark-preview.ts)だけをコピーし、同じ Nix shell と依存を用意する。A が受け付けない `--force` を使用するケースを除外する。

```sh
bun scripts/benchmark-preview.ts dist/benchmarks/baseline.json 15 check tests generate recording wrapper
```

各構成のソースを特定し、入力・端末サイズ・Bun 版・lockfile を揃え、同じマシンで測る。Nix 起動込みのケースは `HAMIO_DEV_SHELL` と `HAMIO_PREVIEW_SHELL` を子プロセスから外して測定する。Nix store は両構成とも温まった状態とし、初回ダウンロード時間とは区別する。
