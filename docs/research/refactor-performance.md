# 実行基盤の性能比較

hamio の API v1 を実装する二つの実行ファイルを対象に、起動、表示生成、event 処理、同時実行、入力応答、サイズを比較した記録である。比較対象を基準版と評価版と呼び、ソースとビルド条件を以下に定める。同じ入力に対する pipe の stdout・stderr は全試行でバイト単位の一致を確認した。人向けフォームは基準版が Clack Prompts、評価版が hamio の renderer を使うため表示が異なる。

## 比較対象と条件

- 基準版: [bb4db186c0e663968463dab3b3e88b7bfa1358d9](https://github.com/9uiLe/hamio/commit/bb4db186c0e663968463dab3b3e88b7bfa1358d9) からビルドした実行ファイル。
- 評価版: [生データ](refactor-performance.json)の `candidateSources` に記録した SHA-256 のソース。実行ファイルの SHA-256 とサイズも同ファイルへ保存する。
- 2026-09-17、macOS 26.2 / Darwin 25.2.0、Apple M1 Pro、10 core、16 GiB RAM、arm64、Bun 1.4.2。両方とも同じ Nix 入力で固定した公式 Bun ランタイム、minify 有効、bytecode・smol なし。
- 各条件・各版2回の warmup 後、新規プロセスを30回ずつ起動する。各組で基準版・評価版の順序を交互に反転する。OS cache は温まった状態で、cold start ではない。
- [benchmark-refactor.ts](../../scripts/benchmark-refactor.ts)で固定入力を生成する。ソースと実行ファイルの測定前後の hash が一致しなければ保存しない。入力 byte 数と hash、全サンプルも記録する。
- wall time は親の `performance.now()` で spawn から終了・出力取得まで測る。CPU は終了した子の `resourceUsage().cpuTime.total` を ms に換算する。maxRSS は同 API の bytes を MiB に換算する。[Bun の測定 API](https://bun.com/reference/bun/Subprocess/resourceUsage)
- p95 は nearest-rank（30個を昇順に並べた29番目）。CPU と maxRSS は中央値。親プロセスの CPU・メモリは含めない。
- 通常のデスクトップ上で測り、電源状態や他プロセスを完全には固定していない。小さい差は測定間の揺れを含む。別の benchmark、build、test は並行実行しない。

表の生成は32部品、各20行×4列の日本語を含む表で、入力61,147 bytes、stderr 63,360 bytes。出力先は pipe のため、端末エミュレーターの描画時間を含まない。stream は100 taskを開始し、指定件数の進捗を送り、100 taskと run を完了する。

## 処理時間・CPU・メモリ

各セルは基準版 → 評価版。4プロセスの wall time は4本すべての完了まで、CPU は各子の合計、maxRSS は各子の peak の合計とする。後者は同時点のメモリや専有物理メモリではない。

| 条件                               |      中央値 ms |         p95 ms |          CPU ms |      maxRSS MiB |
| ---------------------------------- | -------------: | -------------: | --------------: | --------------: |
| 機能照会                           |  17.22 → 16.76 |  18.50 → 17.93 |   15.59 → 15.20 |   20.59 → 20.39 |
| 非対話フォーム                     |  20.49 → 19.78 |  21.56 → 21.78 |   18.90 → 18.37 |   23.16 → 22.97 |
| JSON 表示                          |  20.42 → 18.81 |  21.45 → 19.73 |   19.08 → 17.43 |   23.41 → 22.39 |
| 32表の生成・出力                   |  27.77 → 22.31 |  29.75 → 24.16 |   32.52 → 24.49 |   34.52 → 27.23 |
| 2,000進捗・最終結果のみ            |  27.97 → 23.10 |  30.39 → 24.68 |   40.48 → 28.09 |   41.55 → 31.11 |
| 20,000進捗・全 event 出力          | 110.46 → 47.33 | 116.04 → 48.58 |  188.85 → 81.73 |   61.80 → 52.52 |
| 4プロセス×20,000進捗・最終結果のみ |  85.82 → 52.08 |  97.73 → 68.56 | 544.07 → 310.92 | 217.44 → 189.48 |
| PTY フォーム・日本語入力           |  47.74 → 46.32 |  49.94 → 48.12 |   38.06 → 36.34 |   27.06 → 26.23 |

2万進捗の全 event 出力は中央値57.2%、CPU 56.7%、maxRSS 15.0%減。4プロセス同時実行は中央値39.3%、CPU 42.9%減。32表の生成・出力は中央値19.6%、maxRSS 21.1%減だった。これらは複数の変更をまとめた比較で、個別の最適化への寄与率は分離していない。

機能照会と小さいフォームの起動はほぼ同じ規模で、フォームの p95 は0.22 ms（約1.0%）増えた。すべての処理が一律に高速化したとは判断しない。既定の最終結果は進捗件数に関係なく1 runあたり124 bytes、2万進捗の全 event 出力は2,984,149 bytesで、両版とも同じだった。

## 入力応答と進捗描画

PTY は80列×24行、`TERM=xterm-256color`、色なし。質問の出力を受け取った時点で `日本語` と Enter を送る。人の入力待ちは含めない。

| 区間                           |     中央値 ms |        p95 ms |
| ------------------------------ | ------------: | ------------: |
| 起動から質問の出力まで         | 44.87 → 43.61 | 47.10 → 45.34 |
| 入力送信から成功 JSON 受信まで | 2.225 → 2.107 | 2.498 → 2.333 |

これはフォーム確定までの応答時間であり、各キーの端末への表示反映、IME、画面読み上げの遅延を測るものではない。PTY の出力量は318 → 330 bytesで、評価版は日本語の操作案内と入力カーソルを持つ画面を表示する。

進捗は最大10 fps、書き込み中は最新状態だけを保持する。[実行境界のテスト](../../tests/runtime.test.ts)では、描画前の10,000更新で状態の取得・文字列生成が0回、描画時に1回となること、出力が遅い間の追加10,000更新を積み上げないこと、close 後に再描画しないことを確認する。これは計算回数と寿命の検証であり、実端末の FPS 測定ではない。

## 配布サイズ

| 対象                            | 基準版 bytes | 評価版 bytes |  削減率 |
| ------------------------------- | -----------: | -----------: | ------: |
| minify した JavaScript          |       49,409 |       43,392 |  12.18% |
| Bun を同梱する実行ファイル      |   62,276,466 |   62,259,954 |  0.027% |
| 同じ実行ファイルの gzip level 9 |   25,558,185 |   25,556,503 | 0.0066% |

JavaScript の確認には各版で `bun build src/cli.ts --target bun --minify --outfile dist/refactor/candidate.js` と同じ条件を使う。SHA-256 は基準版が `afdd7d81b6b60f937c70059e40adf0efa34a3d7413141896fcb3faef2f350118`、評価版が `68006098c970d1195eceefd46ba0dcbd8f277040a3e64abf709aac68a7e1ab68`。

基準版は `@clack/prompts` 1.8.1、評価版は `@clack/core` 1.5.1 に直接依存する。Core 以下の推移依存の版・integrity は同じで、評価版の依存パッケージ数は1つ少ない。評価版は Core の render API と hamio の renderer で画面を生成し、色設定を値として渡す。独自 renderer の保守も評価対象とし、PTY 試験と製品プレビューで確認する。[Clack Core](https://bomb.sh/docs/clack/packages/core/)

Bun を含む実行ファイルは約59.4 MiBでほぼ横ばいである。JavaScript の削減だけではランタイム込みのサイズを大きく変えられない。両版とも固定した Bun を同梱し、minify した本体を組み込む。[Bun の実行ファイル仕様](https://bun.com/docs/bundler/executables)

`bun run package` は約24.4 MiBの gzip を生成し、未圧縮に対する転送量を59.0%減らす。これは同じ評価版の圧縮前後の差であり、基準版の gzip に対する改善率ではない。計測には packaging と同じ `node:zlib` の level 9 を使い、生成した gzip のサイズと展開後のバイト列の一致も確認した。圧縮は配布候補を生成する工程で実行し、通常の build・check では実行しない。

## 負荷を減らす構造

- NDJSON は入力 read の中で行を遅延評価し、完全な行のコピーと行ごとの非同期境界を減らす。境界の資源検証は維持し、汎用 JSON 検証を重複させない。
- `--events` と表は16 KiBを目安にまとめて出力する。入力待ちに入る前に受理済み event を排出し、重要な通知、順序、背圧を保持する。
- Session は状態だけを保持し、進捗の snapshot と文字列は実際の描画時に作る。機械モードで端末や質問を初期化しない。
- 契約、処理手順、I/O、表示計算を分離し、呼び出しごとの値を注入する。I/O と timer を持たない規則を端末なしで検証できる。[実装設計](../implementation.md)

## 検証範囲と再測定

この比較は UI プロセスの負荷を対象とする。利用側の JSON 生成、実際のビルドやテストと同時に動く業務全体、30秒待機 CPU、長時間 run、定常 RSS・PSS・macOS footprint、cold start、Linux、他 CPU、端末エミュレーター描画、tokenizer は未測定。基本設計の業務追加時間5%や全性能予算の達成を示す結果ではない。

macOS arm64 で `bun run check` を実行し、39テスト、Lint、format、型検査、プレビュー照合が成功した。契約、同時実行の分離、遅い出力、エラー・キャンセル、PTY、Bun のない PATH での実行を検証した。製品の入力・結果 PNG と GIF は製品 CLI から生成して目視確認した。Linux は同じ試験を CI で実行する構成だが、本比較のローカル検証には含まない。

[開発手順](../development.md#製品試験と性能測定)に従い、基準版と評価版の実行ファイルを別名で保存して測定する。入力・環境・ビルド設定を揃え、生データと測定対象の hash を残す。通常の check・hooks・CI ではベンチマークを走らせない。
