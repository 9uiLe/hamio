# ソフトウェア設計

[基本設計](../../../docs/design.md)の該当箇所を読み、変更する振る舞いと利用側に見える契約を特定する。

## 境界の決め方

- 業務の実行、権限、順序、並列数、再試行は利用側に残す。UI の要求から汎用 runner や workflow engine を導入しない。
- 公開契約には質問・回答・状態・結果の意味を置く。Bun のオブジェクト、UI ライブラリの全設定、任意関数を漏らさない。
- 入力の解析・検証、状態遷移、描画、返却経路を区別する。I/O を必要としない規則は副作用から分けて検証できるようにする。
- 独立して変更する境界には小さい明示契約を置く。同時に変更する内部モデルを、抽象化のためだけに別 package やサービスへ分割しない。

## 検討する失敗

入力不正、未対応版、不足入力、キャンセル、UI 障害、業務失敗を区別する。EOF を業務成功にせず、確認の取得失敗を肯定に置き換えない。

状態や通信を変更する場合は、古い event、重複、順序違反、出力先の停止、親の終了を確認する。機械向けの値と人向け表示が同じ業務状態を表すことを保つ。

## 判断の残し方

変更によって守る契約、公開範囲、依存方向、取り込まない責務を具体例で示す。異なる案に実質的な利点がある場合だけ比較し、設計書を最終仕様へ更新する。

検証は利用側から観測できる回答・エラー・状態遷移を中心にする。内部関数の配置を固定するだけのテストを増やさない。依存追加は保守、起動、配布、サプライチェーンのコストも比較する。
